# CR-2026-001 — Alignement du codec protocolaire avant gel

Statut : proposée, non approuvée. Date : 23 octobre 2026.
Déclencheur : revue 3.4, audit réel codec Rust vs protocol.schema.json.

## Incident et impact

Reply::decode accepte data:null et error:null dans des réponses ok:true alors que B.2 impose des objets si ces champs sont présents et que le schéma les rejette. Envelope::decode accepte capability.result avec payload:{} alors que la spécialisation KTX-PROTOCOL-002 exige capability_request_id et ok. Ces divergences rendent les validations dépendantes du langage. Aucun contrat n'est encore gelé ; aucun artefact publié.

Reproduction : voir docs/evidence/ARCHITECTURE_GATE.md (trois messages JSON complets et résultats). Le petit harness local importe réellement kortex-abi et les mêmes messages passent réellement dans AJV, sans substitution de résultat.

## Correction proposée, sans rupture de B.2

1. Dans crates/kortex-abi/src/wire.rs : refuser un data/error explicitement null, conserver l'absence optionnelle ; valider capability.result (UUID capability_request_id, ok booléen, objet data si présent, HostError si erreur, exclusivité réussite/échec) selon protocol.schema.json. Préserver les sept kinds et toutes les signatures ABI.
2. Dans crates/kortex-abi/tests/wire.rs : ajouter les trois rejets reproduits, leurs variantes positives, les incohérences et tests de parité.
3. Dans tests/contracts/cross-language.test.mjs et shared/rust/src/lib.rs : étendre le contrôle croisé aux enveloppes via kortex-abi, en ajoutant la dépendance locale dans shared/rust/Cargo.toml si nécessaire. Vérifier les catégories de validité, pas seulement les exemples positifs.
4. Actualiser les lockfiles et documents concernés, uniquement les constats et preuves. Aucun endpoint ni permission supplémentaire.

## Alternatives

Assouplir le schéma pour accepter null : rejeté car contraire au type object de B.2. Supprimer la spécialisation de capability.result : rejeté car annule le contrat candidat approuvé en 2.3. Continuer avec la divergence : rejeté, contraire au gate 3.4. Correction candidate avant gel recommandée.

## Migration, compatibilité et preuves en aval

Aucune donnée publiée à migrer. La correction retire des messages invalides acceptés par erreur. Nouveau build guest requis pour inclure le codec corrigé : identifier une nouvelle empreinte, ne pas la remplacer silencieusement dans les preuves 3.0/3.1. Refaire les tests navigateur Chromium/WebKit et Wasmtime sur exactement ce nouveau binaire, les 30 cas de parité et trois nouveaux cas ; refaire tests ABI, schémas, contrats croisés, conformité et revue 3.4. Mettre à jour le hash attendu du banc natif et les preuves par ajout de reprise datée, conserver l'ancien hash et l'historique de commits.

Le plan source demeure inchangé. Les noms de code avant gel restent candidats ; pas de nouvelle ABI majeure nécessaire pour respecter le contrat déjà défini.

## Exécution autorisée et réalisée — 23 octobre 2026

Le propriétaire a autorisé cette correction par « Oui » en réponse à la proposition CR. Les sources/tests prévus ont été corrigés. Aucun accord de gel ou signature au nom des responsables technique/sécurité déduit de cet accord. État : implémentée et vérifiée, revue finale du gate attendue.

Les champs data/error explicitement null sont rejetés, l'absence reste autorisée. capability.result est spécialisé et validé en encodage comme décodage, selon les mêmes règles que Reply ; les longueurs code/message respectent les bornes du schéma.
