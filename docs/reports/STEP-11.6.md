# Rapport 11.6 — Publication à chaud réelle sur Cloudflare

27/10/2026, Windows. Base 524a6b0. Le propriétaire a autorisé l’enchaînement des trois étapes, y compris leur validation sur staging. Commit dans PROGRESS.md ; état technique prouvé, sans fabrication d’une approbation humaine formelle.

Site réel : https://kortex-web-staging.userpgl.workers.dev ; Runtime isolé : https://kortex-run-staging.userpgl.workers.dev ; API/D1/R2 de staging existants et identités vérifiées. Aucun DNS, domaine, service mail ou production modifié. Aucun namespace KV inutile. Staging explicitement noindex.

Runtime Worker ajouté : configuration et archive servies depuis l’origine run, admission via le vrai Service Binding API avant livraison de la frame et du descripteur signé. Clés de confiance de déploiement, CSP frame-ancestors fermée sur le site, sandbox existant, aucun choix de clé/origine depuis un message parent. Le registre d’artefacts est désormais résolu à partir de la fiche publiée : un nouvel ID ne nécessite pas une liste statique reconstruite côté Runtime. Le cache d’archives vérifiées ne contourne pas une révocation de l’API. Le Worker Runtime passe aussi un contrôle TypeScript strict autonome.

`node scripts/web-hot-publish.mjs` a effectué un aller-retour Cloudflare réel : paquet fixture dérivé de l’archive calculatrice vérifiée, nouveau manifeste/contrat ID, signature Ed25519 éphémère, chargement R2 immuable et publication par l’API admin existante. L’opérateur temporaire simule un pipeline CI ; aucune exécution GitHub OIDC n’est revendiquée. Sa clé privée reste uniquement en mémoire et la politique antérieure est restaurée à la fin.

Preuve finale : nouvel outil visible dans la fiche, le catalogue, les actions et le sitemap en **381 ms** au total contrôlé ; 25×48=1200 dans le vrai Runtime Chromium et WebKit ; révocation, disparition et nouveaux lancements refusés en **517 ms** pour fiche/app. Configuration Runtime 404 et archive 410 après révocation. Aucun rebuild ni redéploiement du site entre publication et révocation.

Le premier essai avait recherché l’ID alors que l’API recherche le nom/résumé : assertion du banc corrigée, fixture retirée et politique restaurée avant la nouvelle exécution. La dernière suite locale vérifie l’absence de scripts exécutables inline dans /app.

Deux contrôles Playwright distants finaux vérifient l’état révoqué, l’endpoint interne fermé, le noindex de staging et la recherche réelle.
