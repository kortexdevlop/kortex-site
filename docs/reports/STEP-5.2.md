# Étape 5.2 — Capacités navigateur et IndexedDB

Base 2c17303 ; quatrième étape du lot expressément autorisé. Services navigateur réels, refus par défaut et consentement hôte par outil/version/instance/capacité/ressource, autorisation une fois ou session bornée à cinq minutes, refus explicite et révocation. Approbation acceptée uniquement depuis un événement hôte fiable ; les opérations exigeant un geste démarrent dans cet événement, sans faire confiance à un booléen du guest. Prompts bornés/expirables et tous annulés à la fermeture.

IndexedDB : base par origine hôte dédiée, identité (profil, outil) choisie par hôte, namespaces de version, transactions natives atomiques, quota logique 5 Mio commun aux versions, contrôle de corruption et suppression explicite. Aucun stockage de secret prévu et aucun repli silencieux mémoire/localStorage. Le service tente navigator.storage.persist après consentement avec geste, puis exige persisted=true pour autoriser la durabilité. Une navigation privée ne peut pas être détectée de façon fiable : tout contexte non confirmé persistant est donc refusé UNAVAILABLE, y compris un navigateur normal refusant ce droit. Aucune garantie absolue contre suppression des données par le navigateur/utilisateur.

Fichiers : File reste dans l'hôte ; seul un jeton opaque aléatoire de 256 bits passe dans le JSON. Jetons expirants et révoqués à la fermeture, maximum 128 ; sélection et sauvegarde sur geste, refus 10 Mio+1 ; lecture de blocs <=256 Kio, base64 borné. Sauvegarde Blob/download avec nom sans chemin ; la limite JSON ABI s'applique également au contenu d'une requête de sauvegarde.

Réseau : uniquement HTTPS GET vers allowlist hôte, permission par origine, refus des credentials/URLs privées littérales/redirects, credentials omit, no-referrer, CORS, délai 30 s et réponse <=256 Kio. Aucun mécanisme navigateur ne permet au service de pinner lui-même le DNS ; les origines de l'allowlist sont donc des origines hôtes de confiance. Clipboard : permission hôte + geste fiable + contrôle natif du navigateur, refus stable si absent ou refusé.

Les retours asynchrones sont remis au Worker en capability.result, sans réentrance, puis un nouveau render actualise Dioxus. Révocation annule demandes, lectures/fetch et jetons. Les callbacks conservent l'instance d'origine ; les réponses tardives d'un outil fermé ne peuvent utiliser les permissions du suivant. Le focus réel des onglets Dioxus est également confirmé dans les deux navigateurs.

Validation finale : 22 tests adaptateur et 6 tests Web Chromium/WebKit ; typecheck strict ; cargo check du runtime ; dx build produisant le shell ET tous les bundles adapter/worker/chunks. Le serveur final de tests sert uniquement la distribution produite, sans masquer d'asset manquant via les sources. Aucun mock permanent. Les contrôles positifs de stockage pilotent uniquement la sonde de durabilité en test ; les transactions IndexedDB, permissions, fichiers, réseau, Worker et guest sont réels. La non-disponibilité de persistance est testée séparément. Clipboard peut légitimement être refusé par l'API native ; le test n'affirme pas son fonctionnement lorsqu'elle refuse.

Le banc réseau utilise un vrai endpoint TLS local avec certificat éphémère sous target, car WebKit ne permet pas de simuler une réponse redirect 302 avec route.fulfill. Exception TLS exclusivement dans la configuration de test, jamais dans le service produit. Aucun contenu externe ni déploiement requis.

Ajouts nécessaires : fixture guest SDK sous tests/fixtures/capability-guest et script de construction isolé, config Playwright racine, test focus réel, adaptation du build esbuild pour inclure les bundles dans runtime/web/public/adapter puis dist dx, fichiers générés ignorés. worker.ts gérait déjà la file et capability.result en 5.1 ; raccordement terminé via bridge/host, sans modification inutile du Worker.

Preuves : docs/evidence/web-5.2.md et captures web-5.2-chromium.png/web-5.2-webkit.png. Aucun schéma ou ABI gelé modifié. Linux/macOS et Firefox restent écartés sur demande.
