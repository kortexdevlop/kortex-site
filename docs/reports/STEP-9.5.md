# Étape 9.5 — Publication privée vérifiée

Implémentée et testée le 27 octobre 2026, Windows ; base d3345ce. Lot explicitement autorisé 9.4–9.6, sans prétendre à une revue indépendante.

Les trois POST privés publication/rollback/révocation exigent un JWT signé court (maximum dix minutes), algorithme fixé par l'émetteur, audience/issuer/subject/repository/repository_id/ref/workflow_ref exacts et action autorisée par la politique serveur. Le mode GitHub vérifie RS256 contre le JWKS HTTPS officiel uniquement. Les JWT ne peuvent choisir aucune URL de clés. L'identité alternative Ed25519 épinglée d'opérateur est limitée à local/staging, refusée en production ; la configuration absente échoue en 503, sans secret partagé ni contournement de test applicatif. Les clés privées éphémères des tests existent exclusivement dans les bindings Vitest en mémoire.

La publication valide le corps JSON fermé (256 Kio maximum), les identités, ABI/UI/runtime/permissions, une clé d'artefact active préinstallée, la signature Ed25519 B.2, HEAD/GET conditionnel R2, taille/hash relus avec DigestStream, le ZIP/CRC/chemins/budgets, les métadonnées réellement contenues dans le ZIP et l'ABI WASM statique/validate sans instanciation. Les paquets nouvellement admis sont stored, ordre lexical, timestamps DOS epoch et Unix 0644. L'inspection conserve au maximum 25 Mio de ZIP borné en mémoire ; le hash est incrémental et le chemin download reste purement streaming. Les contrôles ZIP/ABI existants sont partagés avec l'adaptateur Web ; CRC standard optimisé par table, sans changer ses résultats.

Après vérification externe, une unique transaction D1 batch insère la version/actions/artefact, les attestations produites par le serveur, le job uploaded→validated→published, le pointeur et le journal. La migration additive 0003 enregistre acteur/jti/empreinte/réponse avec chaque mutation et empêche toute réécriture. Les erreurs ou collisions annulent l'ensemble. Les répétitions rendent la réponse initiale sans republier ni déplacer un pointeur après rollback/révocation. La révocation courante archive et retire le pointeur dans la même transaction que son tombstone, les autres pointeurs sains restent en place. Le rollback exige une version publiée encore saine, un objet R2 inchangé et expected_current_version vérifié transactionnellement.

Résultats : pnpm --filter @kortex/api test passe 3 tests DTO + 26 tests Worker ; les sept tests publication couvrent claims invalides/algorithmes/signatures/permissions, paquet altéré et métadonnées divergentes, course 200/409, lecture pendant publication encore invisible, rollback CAS, révocation/rejeu sans réactivation, limite de corps. Après contrôle additionnel d'HEAD rollback et optimisation CRC : les 7 tests ciblés repassent, ainsi que typecheck API et adaptateur Web ; le build dry-run API réussit et le gel des six schémas reste intact. Log complet initial : target/validation-9.5-tests.log. Une conversion de type JWK/fixture a été ajustée ; aucune erreur masquée ni test ignoré.

La vérification de publication est réelle dans D1/R2 workerd local avec signatures éphémères et vraies archives ; les tests de JWT GitHub réels nécessitent un runner GitHub. Aucune identité GitHub n'est inventée dans le dossier sans remote. La simulation de staging utilise le canal d'opérateur documenté dans DECISIONS.md. Aucun objet ou compte de production utilisé. L'étape suivante est le gate distant 9.6 ; ses résultats ne sont pas présumés ici.
