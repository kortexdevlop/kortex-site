# Staging Kortex — exploitation et nettoyage

Périmètre autorisé : lot 9.4–9.6, uniquement staging, domaine et messagerie conservés. La production n'a aucun binding configuré et ne doit pas servir de banc d'essai.

Ressources créées le 27 octobre 2026 : Worker kortex-api-staging, base kortex-catalog-staging (ID réel dans api/wrangler.jsonc), bucket kortex-tools-staging. L'API utilise workers.dev ; aucun DNS du domaine n'est ajouté. PUBLIC_WEB_ORIGIN anticipe https://staging.kortex.site, dont le site sera construit plus tard. Bucket sans domaine ni URL publique, Standard, localisation observée Western Europe. La règle fournisseur d'abandon des multipart incomplets après sept jours ne supprime pas les artefacts achevés.

## Exécution et reprise

1. Vérifier le profil kortex et le compte déjà autorisés. `target/cloud-staging-resources.json` conserve les identités créées par cet opérateur ; le script refuse une ressource homonyme non reconnue. Sur un autre poste, vérifier explicitement le compte et ces identités avant de rétablir ce manifeste local, sans copier de jeton.
2. Utiliser Node/pnpm verrouillés et un cache Cargo disposant d'espace. Dans l'environnement Windows utilisé : CARGO_TARGET_DIR=D:/Kortex-build-cache, CARGO_PROFILE_DEV_DEBUG=0, CARGO_PROFILE_TEST_DEBUG=0, CARGO_INCREMENTAL=0.
3. Lancer `node scripts/staging-publication.mjs`. Il vérifie la propriété, prépare les ressources privées, applique les trois migrations D1 distantes, déploie uniquement staging, installe le secret de curseur sans le journaliser et prépare le pipeline de paquets. Le build habituel de l'API demeure un dry-run ; seule cette procédure opérateur de staging déploie réellement.
4. Le script utilise [getPlatformProxy et les remote bindings officiels](https://developers.cloudflare.com/workers/wrangler/api/) pour ses PUT conditionnels R2 et l'installation des clés publiques de staging. La condition If-None-Match est éprouvée réellement : un deuxième PUT divergent doit être refusé. Aucun endpoint d'upload public ni clé S3 permanente n'est créé.
5. Les POST HTTPS traversent l'API réellement déployée. La base finale doit conserver calculatrice 1.0.0 comme version saine et une autre version de staging révoquée ; le téléchargement révoqué doit répondre 410. Le script écrit son rapport local, les octets téléchargés et les seules clés publiques de confiance sous target/staging-cloud. Un échec reste non validé.
6. Construire l'adaptateur Web et le shell local, puis lancer `pnpm exec playwright test -c tests/integration/playwright.staging.config.ts`. Il exige un roundtrip cloud réussi, retélécharge les octets distants et les ouvre dans le shell local avec l'admission cryptographique normale (Chromium/WebKit). Il ne simule pas un site staging déjà livré.
7. Construire le Desktop Windows si nécessaire, puis lancer `tests/integration/staging-desktop.ps1` avec le même cache Cargo. Le test ouvre les octets téléchargés via l'admission native habituelle. Il arrête uniquement le processus qu'il a lancé et restaure ses variables de test. L'accès CDP local sert uniquement au banc d'essai.

L'identité de publication est temporairement un opérateur Ed25519 épinglé, pas un vrai job GitHub. Les clés privées vivent seulement dans le processus puis disparaissent ; les JWT durent cinq minutes. Le JWT d'opérateur et la graine de signature ne sont ni écrits sur disque, ni ajoutés à un argument de commande. Le serveur interdit ce mode en production. La politique persistée ne contient qu'une clé publique éphémère ; une exécution ultérieure autorisée remplace cette politique. Les preuves de signature de ce gate et ses ancres restent TEST, à durée limitée (24 h), sans confiance de production. Une reprise après expiration doit préparer un nouveau jeu de versions/identifiants de clés de staging ; ne jamais prolonger ou réécrire une clé immuable déjà référencée.

Incidents rencontrés : API et CLI de création R2 ont renvoyé 500/10001 ; la création du bucket privé a réussi dans le tableau de bord, puis sa confidentialité a été confirmée via API. Aucun achat ou changement de plan n'a été fait. L'horloge locale était environ six secondes en avance sur le serveur : la nouvelle clé de fixture commence une minute avant sa génération pour le test, sans affaiblir les vérifications temporelles du serveur. Une preuve existante n'est jamais écrasée : chaque clé éphémère reçoit une nouvelle sortie de signature.

## Nettoyage / récupération

Ne pas supprimer automatiquement le staging après ce gate : il est nécessaire aux étapes suivantes. Une révocation retire l'accès public mais conserve le tombstone et le journal. Un rollback remet le pointeur vers une version publiée, encore vérifiée et disponible ; il ne réactive pas une version révoquée. Une ressource homonyme non reconnue ou un compte différent doit interrompre la procédure.

Pour un retrait ultérieurement autorisé : retirer d'abord le Worker staging et ses éventuels domaines propres, puis le bucket de staging et la base dont les identités ont été vérifiées ; conserver la messagerie, la zone et tous les éléments de production. Ne pas réutiliser la procédure de suppression de l'ancien projet comme commande générique. Les données révoquées/orphelines ne sont pas purgées automatiquement et les journaux du fournisseur ne sont pas présentés comme effacés.
